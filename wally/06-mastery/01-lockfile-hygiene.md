# Keeping the tree boring

*Commit the lockfile, read its diff, pin what is expensive to break, and delete it when it wedges.*

Wally · Best Practices & Capstone · 10 min

---

A good dependency tree is one nobody thinks about. It resolves the same way on every machine, it changes only when someone meant it to, and when it does change you can see what moved. All four of the habits in this lesson are in service of that one goal: making an install boring.

The first is the easiest. **Commit `wally.lock` for a place or an app.** The manifest records what you will *accept*; the lockfile records what you actually *got*. `^2.0.0` is satisfied by 2.1.0 today and by 2.4.0 next month, and without the lockfile in version control those are two different builds of the same commit. A library generally does not commit it, and it would make no difference if it did — `wally.lock` is stripped from the published archive.

**wally.lock**

```toml
# This file is automatically @generated by Wally.
# It is not intended for manual editing.
registry = "test"

[[package]]
name = "biff/dungeon"
version = "1.4.0"
dependencies = [["Signal", "sleitnick/signal@2.1.0"], ["UiKit", "biff/ui-kit@3.1.0"]]

[[package]]
name = "sleitnick/signal"
version = "2.1.0"
dependencies = []

[[package]]
name = "biff/ui-kit"
version = "3.1.0"
dependencies = []
```

Short, literal, and no checksums. `registry = "test"` is hardcoded in the writer, so every real lockfile in the world says it — it is not something you did.

## Read the diff

The second habit costs nothing and catches the most. A lockfile diff is a diff like any other, and it is the only place a *transitive* change is visible. One caret bump in the manifest can move a dozen packages you have never heard of, and the manifest diff will show you one line of it.

**One manifest line, two package changes**

```text
 [[package]]
 name = "biff/dungeon"
 version = "1.4.0"
-dependencies = [["Signal", "sleitnick/signal@2.1.0"], ["UiKit", "biff/ui-kit@3.1.0"]]
+dependencies = [["Signal", "sleitnick/signal@2.1.0"], ["UiKit", "biff/ui-kit@3.4.0"]]

 [[package]]
 name = "biff/ui-kit"
-version = "3.1.0"
-dependencies = []
+version = "3.4.0"
+dependencies = [["Signal", "sleitnick/signal@2.1.0"]]
```

The interesting line is the last one: `biff/ui-kit` picked up a dependency on Signal between 3.1.0 and 3.4.0. Nothing in the manifest says that, and nothing but the lockfile diff would tell you.

The third habit is selective. **Pin with `=` where a break would be expensive**, and leave the caret everywhere else. A UI kit whose minor releases quietly change layout, or a data-store wrapper that owns saved player data, is worth an exact requirement; a signal implementation that has been stable for years is not. Pinning everything is not caution, it is just a manifest nobody will ever update.

> **Delete and reinstall is the standard repair**
>
> Wally's resolver is greedy: it walks the graph breadth-first, takes the first version that satisfies a requirement, and **never backtracks**. Locked versions are preferentially reused, so a stale `wally.lock` can activate a version early and then fail against a stricter requirement it meets later — an install that would have succeeded from scratch. Before you go hunting for the conflict, delete `wally.lock` and run `wally install` again. It fixes this more often than anything else you could try.

**Key points**

- Commit `wally.lock` for a place or an app; a library generally does not, and it is stripped from the published archive anyway.
- Read the lockfile's diff like any other diff — it is the only place a transitive change shows up.
- Pin with `=` where a break would be expensive, and leave the caret where it would not.
- The resolver is greedy and never backtracks, so a stale lockfile can wedge an install that would succeed from scratch.
- Delete `wally.lock` and install again is the standard repair; re-run the type restore afterwards.
