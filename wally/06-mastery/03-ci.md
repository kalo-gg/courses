# Continuous integration

*A workflow that installs, restores types, builds and publishes, and notices when a publish fails.*

Wally · Best Practices & Capstone · 10 min

---

Everything this course has taught you to do by hand is something a machine should be doing on every push. Continuous integration for a Wally project is not elaborate — install the toolchain, install the packages, put the types back, build the place — but getting the order right matters, and the last step of a release pipeline has a trap in it that is worth the whole lesson.

**.github/workflows/ci.yml**

```text
name: CI

on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install the toolchain
        uses: CompeyDev/setup-rokit@v0.1.2
      - run: wally install
      - run: rojo sourcemap default.project.json --output sourcemap.json
      - run: wally-package-types --sourcemap sourcemap.json Packages/
      - run: rojo build default.project.json --output place.rbxl
      - uses: actions/upload-artifact@v4
        with:
          name: place
          path: place.rbxl
```

The toolchain step is whatever action runs `rokit install` for you; everything after it is the same four commands you would run locally. `rokit.toml` is what makes the versions the same as yours.

The order is not a style choice. `wally install` **deletes** `Packages/`, `ServerPackages/` and `DevPackages/` before it writes them, so anything a tool put in there is gone. `rojo sourcemap` needs the tree that install just wrote. `wally-package-types` needs the sourcemap that Rojo just wrote. Move any of the three and the build either fails or, worse, succeeds with the exported types silently missing.

> **There is no --locked, so check the lockfile yourself**
>
> `wally install --locked` is documented on Wally's default branch and does not exist in 0.3.2, where `--project-path` is `install`'s only flag. The substitute is one line of git: run `wally install`, then `git diff --exit-code wally.lock`. If the lockfile moved, someone committed a manifest change without the resolution that goes with it, and the job fails — which is exactly what `--locked` would have done for you.

## Publishing on a tag

**The publish job, as most people first write it**

```text
name: Publish

on:
  push:
    tags: ["v*"]

jobs:
  publish:
    if: startsWith(github.ref, 'refs/tags/')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: CompeyDev/setup-rokit@v0.1.2
      - name: Write the Wally auth file
        run: ./scripts/wally-auth.sh
        env:
          WALLY_TOKEN: ${{ secrets.WALLY_TOKEN }}
      - run: wally install
      - name: Publish
        run: wally publish
```

This job is broken, and the rest of the lesson is about why. Note the auth step: 0.3.2 has no `--token` flag — that is documented on the default branch and absent from the release — so the token has to reach Wally's auth file some other way.

The tag gate is the uncontroversial half. Publishing on every push would try to republish a version that already exists and fail, because versions are immutable; publishing on `v*` tags means a release is a deliberate act with a name. The `if:` on the job is belt and braces alongside the `on:` filter, and it costs nothing.

> **A failed publish exits 0**
>
> `wally publish` prints `Error: <status>` and then **returns success**. A CI job that trusts the exit code — which is every CI job, because that is how CI works — goes green on a publish that did not happen. You find out when someone tries to install the version and it is not in the index.

The fix is to stop trusting the exit code and read the output. Capture what `wally publish` prints — including standard error, since that is where the message goes — look for a line that begins with `Error`, and fail the step yourself when you find one. It is four lines of shell, and it is the difference between a release pipeline and a release pipeline that lies to you.

**Key points**

- The pipeline is: install the toolchain, `wally install`, `rojo sourcemap`, `wally-package-types`, then build.
- The type restore must follow every install, because install deletes the three package directories first.
- There is no `--locked` in 0.3.2; `git diff --exit-code wally.lock` after installing does the same job.
- `wally publish` prints `Error: <status>` and exits 0, so a job that trusts the exit code goes green on a failed release.
- Capture the output and fail the step yourself — that is the only reliable signal this release gives you.
