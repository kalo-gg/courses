# Designing a publishable library

*Laying out a Roblox library so it publishes cleanly, tests in Studio and can serve two targets.*

pesde · Best Practices & Capstone · 11 min

---

The capstone ships Loot. Before writing its manifest, decide what each file is *for*, because `includes`, `build_files` and the test place each answer a different question about the same tree: what consumers download, what their sync tool mounts, and what you open in Studio.

**Loot's tree**

```text
loot/
  pesde.toml                 published — the manifest
  pesde.lock                 committed, not published
  README.md                  published — the registry page
  LICENSE                    published
  docs/getting-started.md    published — the docs site
  src/init.luau              published; lib, and build_files = ["src"]
  src/Table.luau             published
  test/smoke.server.luau     Studio only
  test-place.project.json    Studio only
  roblox_packages/           generated by install; never committed
```

## The release checklist

| Question | Answered by |
| --- | --- |
| What do consumers download? | `includes` |
| What does their sync tool mount? | `build_files` |
| What do I open in Studio? | `test-place.project.json` |
| What must never ship? | Nothing in `includes`; and no `default.project.json` at all |
| What do I depend on that consumers should not? | `[dev_dependencies]` |
| What runtime versions did I test with? | `[engines]` |
| Where do the packages sit in the datamodel? | `[place]` |

Two targets from one source is the last decision. Loot's code never touches `game`, so the same `src/` can be published for `roblox` and for `luau`; only `[target]` differs — `build_files` on the Roblox side, nothing extra on the Luau side — and both must carry the same `description`.

The Roblox-only glue (the Studio smoke test) lives in `test/`, outside `includes`, so it never constrains the other target. The two publishes are two runs of `pesde publish` with the manifest's `[target]` edited in between; there is no flag that does both.

**The Roblox target**

```toml
# published as you/loot 1.0.0 for Roblox
[target]
environment = "roblox"
lib = "src/init.luau"
build_files = ["src"]
```

One `[target]` per manifest — a TOML file cannot hold two, which is why this is two publishes and not one.

**The Luau target, same version**

```toml
# the same 1.0.0, published again for standalone Luau
[target]
environment = "luau"
lib = "src/init.luau"
```

Edit the section, publish again. Only the Roblox side carries `build_files`, and both publishes must share the same `description`.

**Key points**

- `includes` = what consumers download; `build_files` = what their sync tool mounts; the test place = what you open.
- Test harness and installed packages stay out of `includes`; `default.project.json` stays out of the package entirely.
- Dev tooling in `[dev_dependencies]`, tested runtimes in `[engines]`, datamodel location in `[place]`.
- One source, two targets: only `[target]` differs, and the description must match.
